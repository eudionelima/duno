Como o DUNO Funciona

O DUNO foi arquitetado para ir além de um repositório estático de vulnerabilidades. A plataforma permite dissecar a anatomia de cada falha através de uma progressão de 4 níveis de segurança e inspeção direta de código-fonte.

PROGRESSÃO DE SEGURANÇA

A Metodologia dos Quatro Níveis

Cada um dos 20 módulos implementa quatro versões independentes do mesmo fluxo. Isso permite comparar diretamente o comportamento do sistema à medida que camadas de controle são introduzidas.

NÍVEL 01

LOW

Código Vulnerável por Padrão

Ausência total de defesas. Concatenação direta de strings, execução pura de comandos, sessões estáticas.

Objetivo Didático: Entender a raiz matemática e lógica da vulnerabilidade sem ruído.
↓
NÍVEL 02

MEDIUM

Mitigação Ingênua (Bypass)

Introdução de filtros por blacklist, remoção de caracteres específicos (ex: <script>) ou regex simplista.

Objetivo Didático: Aprender técnicas de evasão, encoding e entender por que blacklists falham.
↓
NÍVEL 03

HIGH

Defesa Avançada com Falha Lógica

Controles mais sofisticados implementados, mas com brechas de desenho, suposições incorretas de ambiente ou edge cases.

Objetivo Didático: Desenvolver raciocínio crítico para identificar falhas sutis de arquitetura.
↓
NÍVEL 04

IMPOSSIBLE

Implementação Blindada & Padrão Seguro

Aplicação das melhores práticas da indústria: Prepared Statements, tokenização criptográfica, tipagem estrita e sandboxing.

Objetivo Didático: Servir como referência de engenharia segura para correção no mundo real.
Estudo de Caso Prático: Evolução de Defesa em SQL Injection CÓDIGO PYTHON REAL
LOW — Concatenação Direta
# Vulnerável a UNION e OR 1=1
query = f"SELECT * FROM users WHERE id = {user_id}"
cursor.execute(query)
MEDIUM — Blacklist Ingênua
# Bypassável com UNION/**/SELECT ou case variation
filtered = re.sub(r'(union|select)', '', user_id, flags=re.I)
query = f"SELECT * FROM users WHERE id = {filtered}"
cursor.execute(query)
HIGH — Cast sem Prepared Statement
# Resistente a SQLi, mas falha se o parâmetro puder ser string
try:
    clean_id = int(user_id)
except ValueError:
    abort(400)
cursor.execute(f"SELECT * FROM users WHERE id = {clean_id}")
IMPOSSIBLE — Parameterized Query Completo
# Impossível de injetar: dados separados do comando
cursor.execute("SELECT id, username, role FROM users WHERE id = ?", (user_id,))
rows = cursor.fetchall()
⚔️ Attack Concepts (Engenharia Ofensiva)
  • Sinks & Sources:

    Fontes de dados controladas pelo usuário (parâmetros de URL, headers HTTP, cookies) fluindo para pontos de execução crítica (eval, queries SQL, DOM, shell do SO).

  • Taint Analysis:

    Rastreamento do caminho percorrido por uma entrada não confiável através das camadas da aplicação até o consumo final.

  • Context Injection:

    Forçar o interpretador (HTML, SQL, Shell, JSON) a transitar do modo "dado" para o modo "código/instrução executável".

  • Defensive Evasion:

    Uso de encodings (URL, HTML Entities, Base64, Hexadecimal) e variação de sintaxe para burlar mecanismos de inspeção e WAFs.

🛡️ Defensive Concepts (Engenharia Defensiva)
  • Parameterized Queries (Prepared Statements):

    O motor do banco de dados pré-compila a estrutura da consulta antes de associar os valores, tornando impossível a alteração da lógica SQL.

  • Context-Aware Encoding:

    Codificação de caracteres especiais de acordo com o contexto em que são renderizados (HTML Body, Atributo, Script, CSS, URL).

  • Princípio do Menor Privilégio:

    A aplicação e o usuário do banco de dados operam estritamente com as permissões indispensáveis à sua função, limitando o raio de explosão.

  • Defesa em Profundidade:

    Combinação de validação estrita no servidor, cabeçalhos de segurança (CSP, HSTS, X-Content-Type-Options) e sandboxing isolado.

FLUXO DE TRABALHO

Metodologia Recomendada para o Laboratório

01

Reconhecimento

Interaja com o laboratório no navegador. Observe os formulários, métodos HTTP, parâmetros transmitidos e códigos de status retornados.

02

Exploração (PoC)

Formule uma hipótese de vulnerabilidade e construa uma Prova de Conceito (PoC) controlada para confirmar o comportamento anômalo.

03

Code Review

Clique no botão </> View Source para inspecionar exatamente a linha do Python que causou a vulnerabilidade no nível ativo.

04

Comparação & Blindagem

Suba o nível para Impossible e compare as duas implementações para entender o padrão de remediação definitivo.
